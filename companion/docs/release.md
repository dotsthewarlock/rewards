# Release and rollback contract (V0.6)

Development packages are deterministic, versioned by manifest version and exact source commit.

**User-facing version progression:** manifest `version` (major.minor.patch) is the canonical product version; keep `version_name` and the private npm package version consistent (existing packaging validates both). Each new forward publication with material runtime changes must advance the numeric product version relative to the active published Preview: patch for compatible corrections/refinements, minor for substantial new capability, major for a separately authorized major milestone. Set the next version once for a coherent functional release, before its exact CI/package; do not increment for internal commits, CI retries, documentation-only work or each module handoff. Preserve the full commit and distribution identity, immutable release path, checksums and explicit comparison; numeric progression alone never establishes safety, eligibility, actual installation or rollback authority. Prior same-semver verified releases stay valid; explicit rollback to an older exact identity and historical verification remain supported. No new counter, registry, version scheme, auto-update or CI promotion. The next source checkpoint is 0.6.1; the already deployed 0.6.0-dev-1713e98e643e remains immutable and active until another meaningful accepted publication. Do not republish solely to rename it.
 CI uploads the extension ZIP, self-contained bookmarklet text/source, installation page, native checklist, build metadata and SHA-256 manifest only after tests. CI artifacts expire. An architect-accepted coherent Dev checkpoint may be published unchanged as immutable version-specific GitHub Pages assets before native/live acceptance, clearly labeled testing only; this is not V1.0 or a GitHub Release. A green push alone is not promotion. Scope release blockers to the proposed checkpoint and affected capability. A documented fail-closed unsupported merchant workflow, outstanding native/device acceptance or device-specific unresolved attempt is not a blanket Dev publication/development gate. Master may accept and publish a coherent testing-only checkpoint with useful independent improvements and explicit residual limitations after existing exact CI, artifact, privacy, safety, rollback and two-phase hosted gates. Reuse an already accepted exact integrated artifact if only policy/status changed; do not rebuild for administrative commits. No separate limited-purpose channel or approval merely because a capability remains unsupported. Installation/update/switching with unresolved state remains prohibited; native/live acceptance and Stable promotion remain separately gated. No runtime updater, remote executable MV3 code, new host grant, destructive migration or automatic launch.
